【论文阅读；SIGMOD'25】GustANN：单 GPU 下高吞吐、高性价比的十亿规模向量检索

High-Throughput, Cost-Effective Billion-Scale Vector Search with a Single GPU

摘要

近似最近邻检索（ANNS）已广泛应用于众多场景。各类实际业务场景迫切需要高效方案，实现对十亿规模向量的高吞吐检索。基于 SSD 的图结构 ANNS 系统具备达成该目标的潜力，但 CPU 算力不足成为性能瓶颈。本文提出一套以 GPU 为核心、CPU 辅助协同的 ANNS 架构，并设计 GUSTANN—— 一套面向十亿规模、基于图索引的向量检索系统，兼顾高吞吐与高性价比。我们依托三项核心技术实现上述目标：(1) 内存友好型 GPU 内核，优化降低图检索过程中的 GPU 显存占用，以此提升 GPU 与 SSD 的并发能力；(2) CPU 辅助数据传输机制，缓解 GPU 端存在的 PCIe 带宽瓶颈；(3) 基于枢纽点检索的多 SSD 间负载均衡策略。相较于现有 ANNS 系统，GUSTANN 吞吐量至少提升 2.50 倍，性价比提升 2.62 倍（性价比指标采用 $/QPS 衡量）。

一、引言

近似最近邻检索（ANNS）广泛应用于各类场景，例如网页搜索 [29,36]、推荐系统 [45] 以及检索增强生成（RAG）[4,35]。给定一条查询向量，ANNS 会在基于向量数据集预先构建的索引中，查找该查询向量的 k 个近似最近邻。在实际业务系统中，向量数据集规模可达数十亿条（例如微软 [43] 与阿里巴巴 [21] 的业务场景），向量检索吞吐量能够达到约 10 万 QPS（例如谷歌搜索业务 [3]）。因此，学术界与工业界都在积极探索面向十亿规模向量、支持高吞吐的高效检索方案 [18,19,21,30,43,48]。

本文旨在探索以高性价比（即更低的美元 / 查询量 $/QPS）实现十亿规模高吞吐向量检索的可行方案。为此，本文聚焦基于 SSD 的图结构 ANNS 索引 [30,49]，主要基于两点原因：首先，十亿规模向量需要 TB 级存储空间 [21,43]，往往超出单台服务器内存上限。固态硬盘（SSD）每 GB 成本更低、容量更大，相比内存具备更好的性价比；其次，面向高吞吐 ANNS 场景，图结构索引相比其他类型 ANNS 索引（例如基于聚类的索引 [17,18,47]）性价比更高。图索引将向量组织为细粒度图结构，在相同硬件条件下能够实现更优的吞吐量 [21,49]。

然而我们发现，现有的基于 CPU、部署于 SSD 之上的图结构 ANNS 索引（下文称为纯 CPU 架构）难以实现高吞吐，根源在于 CPU 算力瓶颈。在搭载两颗 CPU 的典型系统中 [30]，SSD 带宽仅能跑至 6GB/s（单块 SSD 理论最大带宽的 60%），无法打满一台典型存储服务器上 6~24 块 SSD 的带宽 [9,14]。究其原因，在高吞吐场景下 CPU 整体算力供给不足。具体而言，我们测算得出：即便跑满 CPU 理论峰值算力，这套 ANNS 系统最多也只能打满 3.6 块 SSD 的带宽（详见 3.1 节）。

提升吞吐量的可行思路是利用 GPU 算力。但现有基于 GPU 的 ANNS 方案仍存在诸多局限，可以分为两类架构：

  • CPU 主导、GPU 辅助架构[47,56]：由 CPU 负责图遍历（同时访问 SSD），将向量计算（例如距离计算）卸载至 GPU。对于图结构 ANNS，该方案依旧受限于 CPU 检索带来的性能瓶颈。
  • 纯 GPU 架构[41,48,57]：将图遍历与向量计算全部卸载至 GPU，充分发挥大规模并行能力，解决了上述瓶颈。但该架构仍受制于有限的 GPU 显存与入站数据传输带宽，最多仅能打满 1.7 块 SSD。一方面，想要同时打满 GPU 与 SSD 的性能，需要设置较大批处理规模；但现有系统 [30,48] 需要占用大量 GPU 显存存储访问记录表等查询相关数据结构，使得最大可用批规模仅能达到理想值的 50%。另一方面，纯 GPU 架构由 GPU 内核直接发起 SSD 读取（称为GPU 直访[42]）；即便在理想条件下，通过 PCIe 4.0 总线，GPU 最多只能利用 24GB/s 的 SSD 带宽（约打满 2.4 块 SSD）。

为解决现有架构存在的各类问题，本文提出 GUSTANN¹—— 一套高吞吐、高性价比的图结构 ANNS 系统。系统采用GPU 主导、CPU 辅助架构：GPU 负责图遍历，同时利用 CPU 协助数据传输。该架构的性能不再受限于 CPU 检索；同时可借助 CPU 侧 I/O 调度缓解入站带宽瓶颈。

我们首先优化 GPU 检索的显存占用，以此支撑更大批处理规模，保障 GPU 与 SSD 的高并发执行。具体来说，本文设计显存高效型图遍历 GPU 内核，以少量冗余计算换取更低显存开销。传统基于 CPU 的 ANNS 算法 [21,30,40] 依靠高显存占用的数据结构消除冗余计算，但该思路不适用于 GPU。我们核心观察到：GPU 的 SIMT 架构天然能够承受一定程度的冗余计算。为此我们设计适配 GPU 的图检索并行算法，降低冗余计算带来的开销。该算法不再维护占用大量显存的数据结构（例如访问记录表）来规避重复计算，而是先并行执行全部计算任务（允许存在冗余计算），随后执行并行去重流程，保证算法结果正确。

其次，我们提出CPU 辅助传输机制，缓解 GPU 侧 PCIe 链路的入站带宽瓶颈。GPU 直访方案（例如 BaM [42]）以页为粒度读取数据。但我们观测到：在当前主流真实数据集 [18,31,44,52] 中，单个图节点尺寸通常小于一块 SSD 页，往往不足 SSD 页大小的 1/4。因此，不应整块传输页面数据，而应当选择性向 GPU 传输所需数据。为实现这一目标，GUSTANN 利用 CPU 完成数据筛选与中转传输。具体流程：访问图节点时，首先将对应 SSD 页面读取至 CPU 内存，充分聚合利用 SSD 总带宽；随后仅把目标节点数据从内存传输至 GPU，节约稀缺的 GPU 入站带宽。

第三，我们还发现：当图索引分散存储在多块 SSD 上时，会产生显著的长尾延迟负载不均问题（99 分位延迟在不同 SSD 之间最高相差 2.17 倍），损害 ANNS 整体性能。本文提出枢纽点检索（pivot search） 解决负载失衡。经分析，负载不均根源在于现有图索引采用单入口设计：单入口机制会带来微观负载倾斜。受限于该设计，前几轮遍历仅访问入口节点周边区域；而该区域的节点无法均衡分布在各个 SSD 上。所有查询都必须访问这片区域，使得负载不均衡问题被持续放大。为解决该问题，我们引入枢纽点检索，将查询请求分散至图中不同区域，避免单一区域出现微观负载倾斜。为分散查询流量，枢纽点检索在 GPU 显存中维护一张小型枢纽图；枢纽图由完整向量数据集的随机子集构建，对应原图不同区域。向量检索流程首先执行枢纽点检索，在枢纽图中找到距离查询向量最近的节点，随后从该节点出发执行磁盘上的图检索。

我们在多个公开数据集上对 GUSTANN 开展实验评估，对比三套基于 CPU 的系统（DiskANN [30]、SPANN [18]、Starling [49]）与两套基于 GPU 的系统（BANG [48]、RUMMY [56]）。在单 GPU 搭配 6 块 SSD 的硬件配置下，GUSTANN 实现每秒 24.7 万次十亿规模向量检索，SSD 最大利用率可达 86.7%。对比基于 CPU 的系统，在十亿规模数据集上吞吐量提升最高 6.98 倍；对比基于 GPU 的系统，吞吐量至少提升 2.50 倍。除此之外，GUSTANN 相比其他系统，性价比（$/QPS 衡量）至少提升 2.62 倍。

综上，本文主要贡献如下：

  • 论证 CPU 算力是实现高吞吐 SSD 图结构 ANNS 的性能瓶颈；
  • 明确利用 GPU 与 SSD 构建高吞吐、高性价比图结构 ANNS 面临的各项挑战；
  • 设计 GUSTANN 系统，依托 GPU 与多 SSD 实现高吞吐、高性价比 ANNS 检索。系统包含三大核心模块：面向图检索的高效 GPU 内核、CPU 辅助传输机制、枢纽点检索；
  • 完成 GUSTANN 的工程实现与实验评估，验证其在高吞吐 ANNS 场景下的执行效率，同时证明相较于其他 ANNS 系统具备更优的性价比。

2.2 SSD-based ANNS


现实业务场景通常包含十亿规模向量 [21,43]，构建图索引需要数百 GB 至数 TB 存储空间，往往超出单台服务器内存容量。因此，这类索引一般存储在 SSD 中；相比内存，SSD 容量更大、性价比更高 [27,30,49]。

图 1 展示磁盘上图的存储布局。整张图以多条记录的形式存放于 SSD 页内，一条记录对应一个图节点。每条记录包含高精度向量以及一张近邻列表，列表存储所有近邻节点编号。单个节点的近邻数量上限为全局常量R，以此保证所有记录定长。两条记录不会跨 SSD 页存放，确保读取一条记录仅需要一次 SSD 页读取操作。

算法 1 展示磁盘检索流程，该算法包含多轮迭代（第 8~17 行）。迭代过程中持续维护两组结构：①候选集合S，保存当前找到距离最近的L个候选节点（L为检索长度）；②结果集合E，存储候选节点的精确距离。

检索从固定入口节点p开始，执行多轮迭代。单轮迭代包含下述步骤：①读取当前待探索节点u所在的 SSD 页（第 9 行），从对应记录中解析高精度向量与近邻列表。②标记u为已访问节点（第 10 行），保证每个节点仅被遍历一次。③利用 SSD 读取的高精度向量，计算与查询向量之间的距离，将u插入结果集合（第 11 行）。④遍历u全部近邻节点，借助 PQ 距离（下文说明）将近邻加入候选集合（第 12~15 行）。⑤裁剪候选集合大小至L，限制迭代总次数（第 14 行）。⑥选出与查询向量距离最近的节点作为新一轮待探索节点（第 16 行）。若所有节点均完成遍历，则检索终止，将集合E中距离最近的前k个节点作为近似最近邻结果返回。

为减少高精度向量的读取次数，许多磁盘驻留型图 ANNS 系统会在内存中保存一份经乘积量化（PQ）压缩后的向量副本 [30,34,49]；在将近邻节点加入候选集合时，使用 PQ 距离作为距离近似值（第 13 行）。

三、动机

3.1 CPU 限制近似最近邻搜索（ANNS）的成本效益

现有的基于磁盘的图结构近似最近邻搜索系统无法充分发挥固态硬盘（SSD）的性能。DiskANN [30] 是典型的基于图索引、运行在 SSD 之上的 ANNS 系统。我们测试了它检索过程中的 SSD 读取带宽（5.1 节详细介绍实验配置；为更精准评估算力，本实验关闭超线程，避免超线程之间相互干扰）。图 2 显示，DiskANN 仅能利用 6GB/s 的 SSD 带宽，只达到 SSD 理论最大带宽（10GB/s）的 60%。

尽管 DiskANN 存在 I/O 等待耗时，但我们发现即便将所有 I/O 操作完全重叠，系统性能依旧不理想。在实验中，DiskANN 的一个工作线程大约花费 1/6 的时间执行计算，5/6 的时间从 SSD 读取数据。原因在于 DiskANN 串行遍历图结构；即便实现理想状态下 I/O 与计算完全重叠、不存在 CPU 时间浪费在等待 I/O 的情况，增加计算量依旧无法打满 SSD 带宽（见图 2 中理想系统曲线）。具体来说：理想系统的 CPU 计算耗时是 DiskANN 的 6 倍，最多只能实现 6 倍的 SSD 带宽，约 36GB/s。受限于 CPU 算力，这套理想系统的带宽依旧达不到 6 块 SSD 所能提供的带宽上限（我们的硬件配置中上限为 60GB/s）。

我们的分析表明：CPU 会限制 ANNS 系统的高吞吐性能。这一结论看似和以往观点相悖 —— 此前研究普遍认为，SSD 是基于磁盘的 ANNS 系统的性能主导瓶颈 [19,30,49]。产生分歧的根源在于：以往工作主要面向延迟敏感场景。在这类场景下，为每块 SSD 分配一个 CPU 核心就足够，因为同步 SSD 读取的延迟高于计算耗时，系统总体性能受延迟约束。但想要实现高吞吐，CPU 核心数量必须匹配 SSD 的 I/O 带宽。举例来说，存储服务器通常搭载 6–24 块 SSD [9,14]，想要把全部 SSD 带宽打满，大约需要 94–375 个 CPU 核心（我们这台 56 核服务器最多只能充分利用约 3.6 块 SSD 的带宽），单台服务器很难满足该需求。

CPU 算力不足限制了 ANNS 系统的成本效益。由于单台服务器的 CPU 无法跑满本机 SSD 的带宽，想要达到相同的查询吞吐量（QPS），就需要部署更多服务器，进而抬高 ANNS 服务的部署成本（详见 5.5 节）。

3.2 可行方向：采用 GPU 承载近似最近邻搜索（ANNS）

基于上述观测，我们选择使用 GPU 替代 CPU 构建高吞吐、高性价比的 ANNS 系统，依托 GPU 强大的算力支撑。GPU 采用高度并行的硬件架构，在浮点运算能力（FLOPS）与内存带宽两方面均优于 CPU。例如 NVIDIA A100 显卡，32 位浮点数算力可达 19.5 TFLOPS，显存带宽高达 1935GB/s [6]。与之对比，CPU 的浮点算力低得多（我们评测所用 28 核 CPU 算力仅 1.25 TFLOPS [2]），主存读取带宽通常仅约 30GB/s。

现有的 GPU 加速 ANNS 系统在利用多块 SSD 时存在诸多局限，可以分为两类：
(1) CPU 为主、GPU 辅助架构[47,56]：仅将向量计算（例如距离计算）卸载至 GPU 执行，主体检索流程依旧运行在 CPU 上。对于基于聚类的索引 [56]，该方案具备可行性，因为簇内向量计算密度高；但这套架构用于基于图的索引时会遭遇性能瓶颈 —— 图索引的计算密度相比聚类索引更低。

(2) 纯 GPU 架构[41,48,57]：全部检索任务（包括图遍历与向量计算）均在 GPU 执行，消除了 CPU 检索带来的瓶颈。但该架构受制于有限的 GPU 显存，以及 GPU 入口传输带宽。

为解决上述局限，本文提出GPU 为主、CPU 辅助的架构：检索任务在 GPU 上执行，同时利用 CPU 协助数据传输，有望缓解入口传输带宽不足的瓶颈。但这套架构仍面临多项挑战：

3.3 核心挑战

挑战 1：检索流程内存开销大，制约系统并发能力，对 GPU 与 SSD 两侧均产生负面影响
GPU 与 SSD 硬件原生都具备高并发特性。GPU 依靠海量计算线程实现强大算力：例如 NVIDIA A100 集成 108 个流式多处理器（SM），每个 SM 可同时运行 2048 个线程 [6]。除此之外，现代 SSD 通过并发处理大量请求实现高带宽。因此，GPU 与 SSD 协同工作，需要一套高并发的系统设计。

然而现有基于图索引的 ANNS 系统无法支撑高并发，根源在于内存开销巨大。GPU 显存容量有限（我们实验环境配置为 40GB），其中大部分空间（约 75%）需要用来存放压缩数据集（PQ 量化编码），留给每条查询任务的内存十分紧张。目前绝大多数基于图索引的 ANNS 实现面向 CPU 设计 [21,30,40]，会占用大量内存存储每条查询对应的独立数据结构。现有 GPU 版 ANNS 系统沿用了这套设计 [48,57]。最终，这些数据结构占用大量显存（不同实现方案下占总显存的 28%~45%，详见 4.2 节、5.3 节）。有限的显存降低了可并发执行的查询数量（最大并发数最多下降 50%），进一步导致 GPU 与 SSD 硬件资源无法充分利用。
挑战 2：如何借助 CPU 分担数据传输压力，缓解 GPU 侧带宽瓶颈，这一方向尚未被充分挖掘

纯 GPU 方案会使用 GPU 直访技术，例如 BaM [42]、GPU 直接存储（GDS）[7]，实现 SSD 向 GPU 的直传。但是，将 GPU 直访技术应用于基于图索引的 ANNS，无法取得理想性能。正如图 3 (a) 所示，采用 GPU 直访的基线系统性能仅能达到 GustANN 最大性能的 40% 左右。

经分析，根源在于以 CPU 为中心的 PCIe 拓扑限制了 GPU 高效访问 SSD。所有 PCIe 设备先接入根复合体，再通过高带宽链路连接 CPU 与主存；SSD 与 GPU 之间一般不存在直连通道。这种拓扑造成 SSD 与 GPU 之间双向传输带宽不对称。随着 SSD 数量增多，SSD 聚合带宽可能超出 GPU 入口带宽，此时 GPU 入口带宽就成为瓶颈。图 3 (a) 给出了详细示例。

GPU 直访方案深受带宽不对称问题困扰。以 BaM [42] 为例：如图 3 (b) 所示，当 BaM 作为 ANNS 的 I/O 引擎对接 6 块 SSD 时，SSD 的有效带宽仅能达到理论上限的 27%。这是因为 GPU 直访方案必须经由 PCIe 链路读取完整 SSD 页，而 PCIe 链路带宽最高仅为硬件理论带宽上限的 40%（见图中标注）。

挑战 3：RAID-0 阵列下多块 SSD 之间存在负载不均衡，降低整体检索性能

四、系统设计

4.1 总体概述


GustANN 采用GPU 为主、CPU 辅助架构，实现高吞吐、高性价比的近似最近邻检索（ANNS），整体架构如图 4 所示。

4.1.1 数据布局

GustANN 在磁盘上的数据布局与 DiskANN [30]（见 2.2 节）类似，将向量与邻接信息存储于磁盘。除此之外，GustANN 支持多块 SSD，数据按照 RAID 0 方案组织存储。为解决负载均衡问题（挑战 3），我们引入基准点检索（见 4.4 节），并将基准点图存放于 GPU 显存。同时，绝大多数数据结构（例如压缩向量）从主机内存迁移至 GPU 显存。

主机内存在 GustANN 中的主要用途是充当 CPU 辅助数据传输的中转缓冲区，实现 SSD 向 GPU 的选择性数据传输。该方案不再依赖 GPU 直访技术，能够缓解 GPU 侧 PCIe 带宽瓶颈（4.3 节）。GustANN 利用主机内存主要看重其带宽能力，所需容量远低于其他基于内存的十亿规模 ANNS 系统，因此能够降低服务器部署成本（5.5 节）。

4.1.2 检索流程：单条向量

GustANN 利用 GPU 执行图遍历任务，提升 SSD 带宽利用率，保障检索吞吐量。

初始化阶段：GustANN 初始化查询的流程与 DiskANN 相近。除此之外，系统执行用于负载均衡的基准点检索（详见 4.4 节），确定主检索的入口节点。

检索阶段：检索流程由 CPU 统筹调度，协调 SSD 读取与 GPU 检索运算。为突破 GPU 入口带宽限制，我们借助 CPU 协助发起 SSD 读取流程（4.3 节）。

检索流程大体遵循算法 1（2.2 节）的框架，绝大多数计算迁移至 GPU 执行。检索迭代持续进行，直至候选集合内所有向量均完成探索。每一轮迭代包含两个核心阶段：

(1) SSD 阶段：从 SSD 读取待探索节点u对应的 SSD 页，将页面加载至主机内存，随后把页内所需记录传输至 GPU（4.3 节）。

(2) GPU 阶段：在 GPU 上完成距离计算与数据结构更新。GPU 阶段同时选出下一轮 SSD 阶段需要探索的节点（4.2 节）。

4.1.3 检索流程：批量向量

为支持高吞吐 ANNS，GustANN 将查询打包成批次，充分挖掘 GPU 算力与 SSD 读取带宽。需要说明的是，我们对单条查询的内存占用进行优化（4.2 节），以此支持更大批次，实现更高并发。

然而，批量查询仍无法充分利用 GPU 与 SSD 硬件资源。图遍历过程具有串行特性，阶段之间存在强依赖关系（例如待探索节点依赖 SSD 读取的记录）。因此两个阶段无法并行执行，硬件资源会出现一半闲置的情况。

为进一步挖掘硬件潜力，GustANN 提出查询间流水线机制。不再把所有查询合并为一个超大批次，而是切分为多个微型批次。各个微型批次相互独立，因此不同微型批次可以分别占用两个执行阶段，让全部硬件资源持续工作。

GustANN 并不依赖高性能 CPU 提供大量算力。检索过程中，CPU 的核心任务只是调度与分发各个批次。因此无需配备算力强劲、搭载特殊硬件指令集（例如高级 SIMD 指令）的 CPU。除此之外，核心数量较少的 CPU（例如 8 核）也可以高效运行 GustANN。在我们的实验环境（5.1 节）中，仅需 2 个线程负责向 SSD 与 GPU 发送请求，6 个线程管理 SSD I/O 队列（每个线程向指定 SSD 发送约 200 万 IOPS 请求）。

4.2 节省内存的图遍历核函数

本节通过重新设计面向图近似最近邻搜索（graph ANNS）的 GPU 核函数，解决 3.3 节提出的高内存占用问题（挑战 1）。我们首先分析近似最近邻搜索流程的内存开销；随后指出现有实现存在的缺陷以及我们得到的观测结论；最后提出优化内存占用的搜索算法。

4.2.1 内存开销分析

我们对算法 1 所示搜索流程单次迭代的内存占用进行分析（采用全精度向量的流程开销极小，时间与内存代价可以忽略，故不予讨论；下文仅统计单条查询对应的各类数据结构）：
(1) 从固态硬盘上的记录中读取所有邻居编号；
(2) 借助乘积量化查找表计算乘积量化距离；
(3) 将（邻居编号，乘积量化距离）键值对插入候选集合，候选集合需要保持（部分）有序。

需要注意：为保证算法正确性，候选集合内所有节点编号不能重复。基于 CPU 的传统实现会维护一套辅助数据结构（称为访问记录表），例如哈希表或布隆过滤器 [30,48]，在执行第 (2) 步之前判断节点是否已经被计算过，以此消除冗余计算。

访问记录表占用了大量内存。原因在于：每一轮迭代中，当前正在遍历节点的全部R个邻居都需要存入访问记录表。搜索过程至少需要执行L轮迭代才能遍历候选集合内所有节点，因此至少需要预留能够存放$L \times R$个节点的内存空间。举个例子：当$L=300$、$R=128$，且每个邻居编号占用 4 字节时，访问记录表的内存占用至少为 150KB。在工程实践中，这类数据结构通常需要维持半满状态以避免性能下降，这意味着实际占用大小一般需要翻倍（超过 300KB）。与之对比，候选集合仅存储L个节点（占用 1–2KB）。其余数据结构（记录与乘积量化查找表）在整个搜索过程中占用空间固定（约 40KB）。除此之外，GustANN 需要支持高并发查询（约 40000 条并发查询），仅访问记录表这一项数据结构就需要超过 11.5GB 内存。受限于 GPU 显存容量（本文实验环境为 40GB），再加上其他全局数据结构（例如十亿规模数据集所需乘积量化编码，占用空间超过 30GB）的内存需求，如此巨大的内存开销带来了严峻挑战。

4.2.2 先排序，再去重

占用大量内存的访问记录表受限于 GPU 显存，限制了 GPU 批处理能力，进而降低搜索吞吐。为节省内存，部分 GPU 方案采用线性查找与线性插入策略 [26]，但时间开销通常难以接受。

我们观察得到一条关键结论：在 GPU 上，一定程度的冗余计算是可以接受的。对于 CPU 端近似最近邻搜索，人们习惯在距离计算前剔除重复邻居，避免执行冗余的乘积量化距离计算。然而 GPU 线程以线程束（warp，每个线程束包含 32 个线程）为调度粒度；同一线程束内所有线程必须执行相同指令，或是进入等待状态（即便部分线程理应执行其他分支逻辑）。因此，无需提前消除单一线程内的冗余计算，该线程的计算延迟会被其他线程的执行过程掩盖。

基于该结论，我们调整执行顺序：先完成距离计算与排序，再执行去重。有序数组仅需线性扫描即可完成去重，无需访问记录表这类额外数据结构（详见 4.2.3 节）。同时，GPU 的线程束特性保证：距离计算、排序过程中产生的冗余计算可以被其他线程掩盖，不会引入显著的时间开销。

4.3 CPU辅助数据传输


固态硬盘（SSD）与 GPU 之间的带宽是非对称的，这会降低 SSD 的资源利用率，如图 6 (a) 所示。在 SSD 一侧，由于各个 SSD 不会共享 PCIe 通道，采用 6 块 SSD（本文 5.1 节的实验环境）搭配 PCIe 5.0 x4 接口时，总聚合带宽可达约 60 GB/s。但在 GPU 一侧，NVIDIA A100 通过 PCIe 4.0 x16 链路仅能提供最高 24 GB/s 带宽。因此，GPU 直连访问 SSD 的方案（例如 BaM [42]、GDS [7]）无法充分发挥多块 SSD 的带宽潜力。

为解决该问题，我们观察到算法每一轮迭代仅会使用一条记录，而这条记录的数据量通常不足单个 SSD 页大小的 25%。在检索流程的 GPU 计算阶段，GPU 线程仅读取一条存储在 SSD 上的记录，其大小一般小于 1KB。以 DEEP1B [52] 数据集为例，向量维度为 96 维，向量每一维均为 32 位浮点数；若图的度$R=128$，则单条记录总大小为$text{sizeof(float)} \times 96 + \text{sizeof(int)} \times 128 = 896$字节。与此同时，SSD 的读写粒度为 4KB，意味着检索算法实际用到的数据不足一页的 25%。

基于该现象，我们提出可以向 GPU 选择性传输所需数据。而 GPU 直连访问方案并不支持选择性传输。因此我们借助 CPU 协助完成传输流程，将 CPU 内存（DRAM）作为中转缓冲区，如图 6 (b) 所示。

步骤 1：将完整 SSD 页从 SSD 传输至内存。由于 PCIe 根复合体到内存的传输带宽更高，该方式能够打满 SSD 的全速传输性能。在我们的 6 盘 SSD 测试环境中，4 根内存的带宽能够满足 SSD 合计约 60 GB/s 的聚合带宽需求（5.5.1 节将进一步讨论内存占用情况）。

步骤 2：仅将待拓展节点对应的图记录从内存发送至 GPU。相较于 GPU 直连访问方案，该方法避免向 GPU 传输无用数据，可减少超过 75% 的 GPU 入向带宽压力。例如对于 DEEP1B 数据集，所需 GPU 入向带宽上限仅为$60 \times 25\% = 15\ \text{GB/s}$，该数值处于 GPU 带宽上限范围内。

由此，GPU 入向带宽不再成为数据传输瓶颈，多 SSD 的带宽优势能够被充分利用，从而提升检索吞吐量。与之相对，GPU 直连访问方案只能按照页粒度执行读取操作，会造成 GPU 入向带宽的大量浪费。

需要注意：部分高维数据集（例如 OpenAI Embeddings [5]，维度为 1536）的数据尺寸可能超出 SSD 页大小。但这类高维向量嵌入可以在精度损失很小的前提下压缩至更低维度 [23,34,51,52]。因此，我们可以在存储之前先对其执行降维处理。

4.4 基于枢纽搜索的负载均衡

本节首先分析负载不均衡问题（挑战 3）产生的原因，随后提出基于 GPU 常驻枢纽图的解决方案。

4.4.1 单一入口对多 SSD 场景效率低下

许多基于图的检索方法 [21,30,39] 采用单一入口设计：所有查询均从同一个入口节点开始图遍历。

但是，这种单一入口设计存在明显缺陷，会引发我们所说的微观负载不均衡现象。原因在于：前几轮迭代中，所有查询只会访问图中入口节点周边区域，仅有少量节点存在被访问的可能。例如在十亿规模数据集上，首轮迭代仅访问 103 个节点，第二轮迭代访问 2783 个节点 [31]；被访问节点数量仅占整个数据集规模的约$10^{-6}$。

如此少量的节点极易引发负载不均衡问题。例如在 10000 条向量组成的查询集合中，首轮迭代节点访问次数的中位数为 48，最大访问次数可达 657（相差 13.7 倍）。访问次数的巨大差异会造成各 SSD 性能表现参差不齐，尤其是尾部延迟显著恶化，如图 3 (c) 所示。在单一入口架构下，所有查询都必须访问这片区域，进一步放大了负载不均衡问题。

4.4.2 解决方案：GPU 常驻枢纽图

基于上述分析，我们认为应当将查询分散至图的不同区域，而非全部集中在入口节点附近区域。该方案具备两点优势：第一，有效缓解负载不均衡。各个区域包含的节点数量更少，访问次数的差异会显著缩小；第二，单一入口图检索的前几轮迭代目标是找到查询的 Top-1 近邻 [55]，若检索起点选取距离查询近邻更近的区域，能够提升检索速度。

为找到更近的起始区域，本文引入枢纽搜索（pivot search） 技术：我们从数据集中随机选取若干枢纽向量（例如十亿规模数据集选取 0.1% 的数据）代表不同区域，并在 GPU 显存中构建一张GPU 常驻枢纽图G'。对于一条查询，首先在枢纽图G'上执行 Top-1 检索（即枢纽搜索）；将检索结果（采样集合中距离最近的向量）作为 SSD 驻存大图检索的入口节点。

枢纽搜索采用与 4.2 节相近的检索流程，这里说明几处关键差异：
(1) 为降低整体检索开销，采用更小的检索长度（即候选集合大小，默认值为 4）。原因是枢纽搜索不需要保证近邻具备高召回率；
(2) 使用全精度向量，而非量化 PQ 编码。因为枢纽图本身内存占用较低；
(3) 使用选择排序，而非归并排序。由于检索长度很小，在该场景下选择排序具备更优的并行能力。
值得说明的是，Starling [49] 同样使用一种名为导航图的相似技术来减少 SSD IO 次数。但 GusτANN 与 Starling 存在两点核心区别：
(1) GusτANN 提出GPU 常驻枢纽图，用于解决单一入口架构引发的 SSD 负载不均衡问题；
(2) GusτANN 使用 GPU 执行枢纽搜索，而非 CPU。
因此，如上所述，本文采用一套完全基于 GPU 的检索流程。

4.5 讨论

4.5.1 数据规模的可扩展性

本节通过分析 GusτANN 的存储开销，探讨其扩容至更大数据规模的可行性。GusτANN 主要使用 SSD 与 GPU 显存，对内存 DRAM 需求很低（检索流程中转缓冲区仅占用约 200MB）。

在 SSD 侧，我们按照图 1 所示方式存储向量与图索引。十亿规模数据集（例如 DEEP1B [52]）大约占用 950GB SSD 空间。现代 SSD 容量可达数 TB（我们实验环境中单盘容量为 3.84TB），因此 SSD 不会成为扩容瓶颈。

GPU 显存主要承担两项任务。第一部分是用于距离近似计算的压缩向量。每条 PQ 压缩向量占用 32 字节，十亿规模数据集大约需要 30GB 显存。为支持更大规模数据集，近年来 LVQ [15]、RabitQ [22,24] 等量化技术能够进一步降低压缩向量的显存占用（例如从 32 字节降至 16 字节）。这类方案可将支持的数据规模提升一倍，并且与 GusτANN 相互兼容、互不冲突。

GPU 显存还需要维护查询的检索状态。GusτANN 通过高效的去重算法，将单条查询的显存开销控制在约 40KB，为承载更大数据集预留了显存空间。

另一种扩容思路是提升 GPU 显存容量。举例来说，如果配备 80GB 显存（为本实验环境显存容量的 2 倍），GusτANN 能够在不损失性能的前提下支持 20 亿条向量。

结合显存扩容（2 倍）与更优量化方案，单块 GPU 最多可以支撑 40 亿条向量。

4.5.2 技术方案的通用性

虽然 GusτANN 面向SSD 外存 + GPU的近似最近邻检索场景进行优化，但部分思路可以推广至其他问题：

  • 4.2 节提出了一种显存开销较低的 GPU 端去重实现思路。GPU 上其他去重任务均可借鉴该方案（例如实现 DISTINCT 约束）。这套去重算法包含两项具备通用性的核心技术：① GPU 数据库并行谓词求值（图 5 步骤 i）；② 基于线程束指令、运行在 GPU 上的前缀和计算（步骤 ii~iv）。
  • 4.3 节提出 CPU 辅助选择性传输机制。该方案可以推广，缓解从 SSD 向 GPU 传输数据时的读放大问题；同样适用于依托 GPU 加速计算的 SSD 数据库场景（例如 GPU 仅对 SSD 读取数据的筛选子集开展运算）。

4.5.3 局限性

为充分发挥 GPU 与 SSD 的并行处理能力，GusτANN 在检索延迟上做出了权衡（达到最大吞吐量时检索延迟约 140 毫秒，详见 5.6 节）。

但诸如 RAG 这类新兴应用对延迟并不敏感：整个链路的耗时主要来自大语言模型 LLM（例如 LLM 预填充阶段耗时区间为 100ms~1s）[32,38]。另一方面，随着 LLM 与 RAG 应用需求持续增长，这类场景下的近似最近邻检索（ANNS）面临极高的吞吐量要求。我们认为 GusτANN 在吞吐量与延迟之间实现了良好平衡。

部分传统 ANNS 业务场景（例如网页搜索、推荐系统）属于延迟敏感型业务（通常要求延迟在 10 毫秒级别）[21,30]。在这类场景中，严苛的延迟约束会导致 GusτANN 无法跑满最大吞吐量。

5.1 实验环境配置

基础硬件与系统配置。我们使用如下服务器开展评估实验：

  • CPU：2 颗 28 核英特尔至强 Gold 5420+；
  • 内存：256GB（8 条 32GB DDR5 4800MT/s）；
  • SSD：6 块三星 PM1743 3.84TB 固态硬盘；
  • GPU：NVIDIA A100-40GB；
  • 操作系统：Ubuntu 22.04 LTS，Linux 内核 6.2.0；
  • CUDA 版本：12.3。
    数据集。本次评估采用 4 个广泛使用的公开数据集：
  • SIFT1B [31]：包含 10 亿条 128 维 uint8 类型向量，查询集规模为 10000 条；
  • DEEP1B [52]：包含 10 亿条 96 维 float 类型向量，查询集规模为 10000 条；
  • SIFT100M [31]：SIFT1B 的子集，包含 1 亿条向量，与 SIFT1B 共用同一查询集；
  • DEEP100M [52]：DEEP1B 的子集，包含 1 亿条向量，与 DEEP1B 共用同一查询集。
    对比系统。本文将 GusτANN 与两类 ANNS 系统进行对比：（1）基于 CPU+SSD 的 ANNS 系统；（2）基于 GPU + 内存 DRAM 的 ANNS 系统。

对于CPU+SSD 架构的 ANNS 系统，选取 DiskANN、Starling 与 SPANN 参与对比。这类系统将索引存储于 SSD，依靠 CPU 完成计算。DiskANN [30] 是基于图结构、索引驻留 SSD 的 CPU 端 ANNS 系统。Starling [49] 通过重构 SSD 索引布局与检索流程改进 DiskANN；除此之外，Starling 引入导航图，减少 SSD IO 访问次数。SPANN [18] 是基于聚类的 CPU 端 ANNS 系统。聚类类方法将向量划分至多个聚类簇，针对查询仅在选定簇内进行检索。SPANN 利用 SSD 存储聚类后的向量。

为将向量索引存放在 SSD 上，GusτANN、DiskANN、Starling 拥有结构相近的索引；针对 SIFT100M/DEEP100M 数据集，三者分别需要约 65GB/95GB 存储空间。SPANN 在这两个数据集上需要约 87GB/235GB 存储空间。对于十亿规模数据集，存储需求约为亿级数据集的 10 倍（例如 GusτANN 在两个十亿数据集上均需要约 650GB/950GB 存储空间）。

对于GPU + 内存 DRAM 架构的 ANNS 系统，实验选取 BANG 与 RUMMY 作为对比对象。BANG [48] 是近年提出的基于图结构的 ANNS 系统，RUMMY [56] 是基于聚类的 ANNS 系统；二者将索引存放于内存 DRAM，依靠 GPU 执行计算。BANG 采用和 DiskANN 风格一致的图索引，所需内存容量相近（即 SIFT100M/DEEP100M 分别占用约 65GB/95GB 内存）；RUMMY 在 DEEP100M 数据集上需要约 36GB 内存，主要用于存放数据集。

参数设置。GusτANN、DiskANN、Starling 使用 Vamana [30] 算法构建相同的 SSD 图索引，核心建图参数(R=128)，(L=200)；Starling 额外执行索引重排操作。PQ 编码长度设为 32 字节，保证十亿规模数据集的编码可以载入 GPU 显存。DiskANN 与 Starling 采用束搜索（同时读取W个待探索节点对应的 SSD 页），W取值为 4。BANG 的实现限制邻居节点最大数量为 64，因此我们设置(R=64)构建 BANG 索引，并参照其开源代码建议，将 PQ 编码长度设置为 64 字节。

针对 GusτANN 所使用的基准图（pivot graph），我们随机选取 100 万条向量构建导航图，建图参数(R=32)，(L=50)。该导航图同样供给 Starling 使用，二者图结构相似。为保证对比公平，我们为 DiskANN 缓存 100 万图节点。

SPANN 参照文献 [50] 给出的配置完成索引构建与检索。针对 RUMMY，我们修改其开源仓库中的配置以实现更高吞吐量；训练数据比例固定为 1%（共 100 万条向量）。

CPU+SSD 架构的系统依靠文件系统持久化 SSD 索引，因此我们在 SSD 上部署 ext4 文件系统，并搭建 RAID 0 阵列支持多盘并发。GusτANN 采用 SPDK [13] 获取高性能 SSD 读取能力。

检索阶段：除 GusτANN 外，所有对比系统均占用实验服务器全部 112 个线程（包含超线程）。注意：GusτANN 检索阶段仅使用 8 个 CPU 核心，其中 2 个核心处理查询请求，6 个核心管理 SSD IO 队列。GusτANN 采用多小批次机制（§4.1.3）。若无特殊说明，我们在 2 条 CPU 线程上并发运行 40 个小批次，单个小批次处理 1120 条向量查询。
评估指标。实验主要对比以下三项指标：

  1. 检索吞吐量与精度：检索吞吐量单位为查询数每秒（QPS）；检索精度采用 recall@k 衡量。我们循环重复发送查询向量，以获得更精确的测量结果。
  2. SSD 带宽：系统每秒实际读取的 SSD 页面数据量，单位 GB/s。注意：BANG、RUMMY 检索依托内存而非 SSD，因此不对比该指标。
  3. 性价比：搭建服务器所需硬件成本 ÷ 系统能够提供的检索吞吐量，单位美元每 QPS（$/QPS）。

5.2 整体性能

本节展示 GusτANN 及对比系统的整体性能。我们向 ANNS 系统输入查询集内向量执行检索，测量不同召回率下的检索吞吐量与 SSD 带宽占用。

5.2.1 亿级规模数据集（100M）



SIFT100M、DEEP100M 数据集的实验结果分别如图 7、图 8 所示，我们得到如下结论：

首先，相较于所有 CPU 端方法（DiskANN、Starling、SPANN）以及 GPU 端基于聚类的 RUMMY，GusτANN 拥有更高吞吐量。

在 SIFT100M 数据集、recall@10=0.9 条件下，相较于 CPU 端基于图检索的 DiskANN/Starling，GusτANN 检索吞吐量分别提升 6.70 倍、8.03 倍。原因在于 GPU 可以充分利用多块 SSD 聚合带宽；CPU 端无法实现这一点。DiskANN 不会在单线程内重叠 CPU 计算与 SSD 读取；并且如 §3.1 分析，即便 CPU 充分并行，依旧无法打满 SSD 带宽。Starling 引入流水线技术：在本轮迭代计算当前页其余向量的同时，预读取下一轮迭代所需页面。但是该方案带来的吞吐量提升有限，存在两点缺陷：第一，引入大量冗余计算；第二，流水线无法完全掩盖 IO 延迟。

GusτANN 性能同样超越 CPU 与 GPU 上所有基于聚类的 ANNS 系统。在 DEEP100M 数据集、recall@10=0.9 条件下，GusτANN 吞吐量是 SPANN 的 55.69 倍、RUMMY 的 46.86 倍。根本原因：聚类型 ANNS 每条查询需要扫描远多于图检索方案的向量。举例来说，在 DEEP100M 数据集达到 recall@10=0.9 精度时，基于图的 ANNS 通常仅需遍历约 50 个高精度向量节点；而聚类 ANNS 需要扫描约 6000 条向量。额外产生的计算开销与 IO 开销限制了聚类方案的检索吞吐量上限。

其次，GusτANN 性能优于其他 GPU 端图检索算法。在 SIFT100M 数据集 recall@10=0.9 条件下，GusτANN 吞吐量相比 BANG 提升 2.50 倍，主要有几点原因：（1）尽管内存 DRAM 读取带宽高于 SSD，但数据向 GPU 传输时，PCIe 入站带宽成为全局读取带宽瓶颈；（2）BANG 的 CPU 与 GPU 协同调度较差，频繁在 CPU 与 GPU 之间拷贝数据，数据拷贝操作无法和 GPU 上其他计算充分重叠。最终 BANG 的 GPU 利用率偏低（43.0%，而 GusτANN 可达 68.6%），检索效率不及 GusτANN。

第三，GusτANN 能够实现极高的 SSD 利用率。相较于其他基于 SSD 的 ANNS 系统，GusτANN 多 SSD 聚合利用率显著更高。两块数据集测试中，GusτANN 最高 SSD 带宽利用率可达 83.6%（单盘读取带宽上限 10GB/s）。DiskANN 与 Starling 最大带宽利用率分别仅有 13.4% 与 11.1%，根源是计算与 IO 流水线调度不完善，更关键的瓶颈在于 CPU 算力不足。

SPANN 的 SSD 最大带宽利用率（18.0%）高于 DiskANN 与 Starling，得益于更加友好的 IO 访问模式（并行读取多个页面，而非单次只读一页）。但是代价是 SSD 读取总量远高于图检索方法：SIFT100M 数据集 recall@10=0.9 场景下，SPANN 平均每条查询读取 147.9 个页面，而 GusτANN 仅读取 31.8 个页面。因此即便 SSD 利用率更高，聚类型 ANNS 依旧无法达到图检索 ANNS 同等水平的吞吐量。

5.2.2 十亿级规模数据集（1B）


针对两个十亿规模数据集，我们仅将 GusτANN 与 DiskANN 对比。其余对比系统在建索引或检索阶段需要极大内存，超出本实验服务器内存上限，因此不在十亿数据集上开展对比。

图 9、图 10 分别展示 SIFT1B、DEEP1B 数据集结果。GusτANN 具备良好的大数据集扩展性，在十亿规模数据集上依旧可以维持较高吞吐量。对比 SIFT100M，在 SIFT1B 数据集同等 recall@10=0.9 条件下，GusτANN 吞吐量保留原有水平的 65%。吞吐量下降主要来源于检索路径长度增加；当设置和 SIFT100M 一致的检索路径长度时，GusτANN 在 SIFT1B 上可以实现几乎相同的吞吐量。

在 SIFT1B 数据集 recall@10=0.9 条件下，GusτANN 吞吐量相比 DiskANN 提升 7.81 倍；DEEP1B 数据集场景提升 6.98 倍。SSD 带宽层面，GusτANN 依旧维持相近的磁盘利用率，峰值可达 86.7%；而 DiskANN 在 SIFT1B 数据集上最高仅 13.7%。

5.3 分项拆解分析

本节逐一分析 GusτANN 提出的三大核心设计带来的性能增益。

5.3.1 GPU 检索阶段内存开销

为验证 GusτANN「排序后去重方案（§4.2）」的显存高效性，我们将其与采用布隆过滤器实现重复检测的 BANG 对比。实验使用 SIFT100M 数据集，参数(k=10)，(L=100)。我们统计两套系统单条查询占用的 GPU 全局内存（PQ 编码等所有查询共享的全局内存不计入统计）。BANG 单查询内存占用 480KB，GusτANN 仅占用 40.22KB，内存使用效率是 BANG 的 11.93 倍。

内存开销差距主要来自访问节点记录表。BANG 为该结构分配约 390KB 内存。尽管 BANG 借助布隆过滤器降低内存占用，仍然存在两大缺陷：（1）布隆过滤器存在误报，降低检索效率；（2）为压低误报率，哈希桶容量必须设置较大。与之相比，GusτANN 采用无近似的精确去重算法：（1）不存在近似误差；（2）去重过程无需额外临时内存。

最终，当并发 40000 条查询（充分打满流水线、跑满 SSD 带宽所需最小并发量）时，GusτANN 仅占用 1.53GB 显存（占 40GB 显存总量 3.8%）；BANG 需要占用 18.3GB 显存（占 45%）。十亿数据集还需要为全局结构预留显存（例如 PQ 编码占用约 30GB 显存），BANG 巨大的内存开销限制系统并发能力（最大批处理规模下降 50%）。

除此之外，GusτANN 针对查询私有数据结构具备更优的缓存亲和性，流式多处理器内线程可高频访问相关数据。

5.3.2 CPU 辅助数据传输机制的效果

为证明 CPU 辅助传输方案（§4.3）的有效性，我们将 GusτANN 与GPU 直连 SSD方案对比。我们实现 GusτANN 衍生版本 BaM-ANN，采用前沿 GPU 直访 SSD 系统 BaM [42] 直接从 SSD 读取数据。本次实验不选用 NVIDIA GPU 直接存储（GDS）[7]，相关文献证明：在磁盘 ANNS 典型 4KB 随机负载下，BaM 性能优于 GDS [42]。BaM 依靠 GPU 硬件调度器掩盖直连 IO 延迟，不经过 CPU 流水线。

图 11 (a) 展示 SIFT100M 数据集结果：GusτANN 持续优于 BaM-ANN，性能提升区间 2.50~2.71 倍。图 11 (b) 展示 SSD 带宽与 PCIe 带宽占用情况。依托 DRAM 缓冲实现的选择性传输机制，GusτANN 向 GPU 传输的数据量远小于 SSD 原始读取量，因此流向 GPU 的 PCIe 带宽需求仅为 SSD 带宽的约 28.6%。

与之相反，BaM-ANN 必须将完整 SSD 页面传输至 GPU，页面中包含本轮检索不需要的数据。最终流向 GPU 的 PCIe 带宽需求和 SSD 读取带宽持平（图中数值更高是因为包含其他附加传输数据）。PCIe 总带宽上限低于多 SSD 聚合带宽，因此整套传输链路被 GPU 入站 PCIe 带宽瓶颈限制。

5.3.3 基准图检索（Pivot Search）的作用

为探究基准图检索（§4.4）对 SSD 带宽利用率带来的影响，我们移除 GusτANN 的基准导航图，和原版 GusτANN 进行对照实验。

图 12 展示 SIFT1B 数据集、(k=10)条件下检索吞吐量与 SSD 带宽测试结果。实验发现：基准图检索最高可将检索吞吐量提升 1.50 倍，SSD 带宽提升 1.23 倍。基准导航图通过负载均衡优化 SSD 利用率。图 13 展示(L=30)时 SSD 访问延迟分布：引入基准检索后，访问延迟的离散程度显著降低，批次内部负载不均衡问题得到改善。同时我们观察到，在较低召回率场景下优化效果更加突出。原因是该场景检索路径长度较短，检索性能更容易受到入口节点附近负载不均衡问题的干扰。

5.4 敏感性分析



向量维度。随着向量维度升高，CPU 辅助传输机制（§4.3）带来的性能增益逐步衰减。为量化该影响，我们基于 DEEP100M 向量构造更高维向量（例如将 96 维向量自拼接，得到 192 维向量）。我们逐步增大记录尺寸（向量大小 + 邻居信息大小），从原始大小一直提升至完整 4KB 页大小。图 14 展示 recall@10=0.9 下的实验结果。吞吐量与 SSD 带宽出现下降有两点原因：（1）单页内有效传输数据占比持续上升，削弱选择性传输收益，系统带宽逐步受限于 PCIe；（2）更高维度带来额外距离计算开销，进一步压低吞吐量。DiskANN 的吞吐量与带宽不受向量维度变化影响，因为该方案始终将完整 SSD 页面读取至 CPU 内存。
SSD 数量。图 15 基于 SIFT100M 数据集、recall@10=0.9 条件，对比了 GustANN 与 DiskANN 在不同 SSD 数量配置下的性能。随着 SSD 数量增加，GustANN 的吞吐量与 SSD 带宽均呈现稳定的可扩展性。与之相对，无论配置多少块 SSD，DiskANN 最多只能利用单块 SSD 60%–70% 的带宽上限。
查询集规模。GustANN 的性能不受查询集规模影响，表现稳定。本文所用原始数据集仅包含 10000 条查询向量，但 GustANN 可同时处理超过 40000 条并发查询。为消除整个检索过程中潜在的缓存效应，我们基于 SIFT1B 的查询向量构建了包含(10^6)条查询向量的查询集，并在 SIFT1B 数据集上执行检索测试。
实验结果如图 16 所示。即便面对更大规模的查询向量，GustANN 能够实现与原始小规模查询集相近的检索吞吐量；采用与 5.2 节相同的检索长度参数时，其性能依旧高出 DiskANN 6.08–9.65 倍。GustANN 的 SSD 最大利用率可达 79.1%。

5.5 成本分析

本节首先分析 GustANN 的硬件资源占用情况，随后在十亿规模近似最近邻检索（ANNS）场景下，将其性价比与其他 ANNS 系统进行对比。

5.5.1 硬件资源占用

在不降低检索性能的前提下，GustANN 所需硬件资源（CPU 与内存）可低于 5.1 节给出的配置。
CPU
如 4.1.3 节所述，GustANN 占用的 CPU 核心数量很少（实验中仅使用 8 核）。因此，性能偏弱的 CPU（例如英特尔至强银牌 4410Y，其主频与 5.1 节所用 CPU 一致，但核心数更少）即可满足运行需求。
内存（DRAM）
GustANN 最大占用 33GB 内存空间（大部分用于初始化阶段向 GPU 传输数据；检索阶段仅需约 200MB 作为 4.3 节提及的跳转缓冲区），内存写入带宽需求 61GB/s，读取带宽需求 13GB/s。此外，GustANN 执行检索时，仅使用单个 NUMA 节点的内存。因此，单个 NUMA 节点上的 4 条内存（总计 128GB）便可满足需求。
除此之外，GustANN 其余硬件配置与 5.1 节描述一致。

六、相关工作

基于 SSD 存储的近似最近邻检索（SSD-resident ANNS）
为支撑十亿规模数据集的近似最近邻检索，已有研究利用 SSD 存储索引，避免将 TB 级索引全部载入内存 [18,30,46,49,54]。DiskANN [30] 将图索引存放于 SSD 中，通过同时优化索引构建与检索算法降低检索延迟。Starling [49] 对磁盘索引重新排布，把邻近节点放置在同一个 SSD 页内，进一步减少磁盘 I/O 次数。SPANN [18] 针对基于聚类的近似最近邻检索设计高效磁盘索引，允许在邻近聚类中复制向量。

上述工作面向低延迟优先的 ANNS 场景，但受限于 CPU 算力，难以实现十万级高吞吐量。与之不同，本文借助 GPU 在基于图的 ANNS 中充分利用多块 SSD，实现更高的 I/O 效率与吞吐量。FusionANNS [47] 利用 GPU 实现基于聚类的磁盘 ANNS，然而聚类类方法粒度较粗，I/O 效率低于基于图结构的 GustANN。
GPU 上的近似最近邻检索（ANNS on GPU）

大量研究探索了在 GPU 上运行基于图 [26,41,48,57] 与基于聚类 [33,56] 的近似最近邻检索算法。近期研究也开始探索面向更大规模数据集的 GPU 检索方案。
BANG [48] 通过协同调度 CPU 与 GPU 计算，为大规模数据集提供图索引支持。RUMMY [56] 对基于聚类的 FAISS [33] 进行流水线优化，调度 GPU 与内存间的数据传输，使其能够处理大规模数据集。但这些方案均将索引存放于内存或者显存中，硬件性价比偏低。除此之外，GustANN 对 GPU 图检索算法进行优化，缓解显存容量受限的问题，同时获得更优的并发处理能力。

七、结论

本文提出一种以 GPU 为核心、CPU 辅助的近似最近邻检索架构，实现了 GustANN—— 一套面向高吞吐量、高性价比的十亿规模近似最近邻检索系统。实验结果表明，相较于现有主流系统，GustANN 能够取得更高的检索吞吐量，同时具备更优异的硬件性价比。
